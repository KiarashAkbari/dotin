========================================================================
patch 0014's gates: the refusal fix red and green, the offline suite, and a server
========================================================================
what produced this file, in one command (from ``term-3/answers/stage-4-kiarash-akbari/``; the
interpreter needs the dev
extra only for section 3, which is the half that talks to a real socket)::

    python3 docs/evidence/patch-0014-run.py | tee docs/evidence/patch-0014-run.txt

read it as:

* section 1 is the whole offline suite on the plain interpreter -- no ``psycopg``, no server, no
  network. The tally line is the suite's own, and the elapsed clause is scrubbed so two runs of
  this file can be compared byte for byte;
* section 2 is the red/green half, and the red half is not a story: the harness copies ``src``,
  ``tests``, ``config``, ``sql`` and ``docs/evidence`` into a scratch directory, removes the
  ``try``/``except`` from ``features.connect`` *there*, and runs the new tests against that tree.
  Four of six fail, with the driver's own exception escaping -- the bug, reproduced. It then
  runs the same six against the tree as shipped and they pass. Copying only ``src`` would have
  printed a green for the red run, because the test modules put ``<stage>/src`` on ``sys.path``
  themselves; that is written into the harness's docstring so the next one does not repeat it;
* section 3 starts a disposable cluster, applies stage-2's DDL and this stage's five migrations,
  loads the audit through the shipped loader, seeds 200 synthetic orders so the match-rate view
  has a denominator that is not zero, and runs ``capstone external --report`` twice: once
  against the live socket (exit 0, ``0 of 200`` keys) and once against ``127.0.0.1:5599``, which
  is closed -- exit 67, one sentence, no traceback, and the password from the URI not present in
  the output. The corpus is synthetic and the machine is the agent sandbox («سندباکس»); no
  timing in this file is a stage measurement, and the one that closed 5.3 is
  ``frame-performance-student-run.txt``;
* section 4 is the two touched modules with ``CAPSTONE_DATABASE_URI`` set: ``Ran 90 ... OK
  (skipped=1)``. The skip is the endpoint guard, which needs ``CAPSTONE_EXTERNAL_LIVE=1``. The
  student's own run of the same two modules printed ``Ran 84 ... OK (skipped=1)`` -- 84 because
  the six tests in this patch had not landed yet, and ``skipped=1`` for the same reason as here.
  The 0013 capture's ``skipped=2`` is neither better nor worse: that run's demo step had already
  stored twenty external rows, so the empty-table guard skipped itself. Which live guards get to
  run depends on what the table holds, and that is the whole difference;
* ``check[...]`` lines are the harness asserting its own expectations against the children's output,
  so a silent regression prints ``FAILED`` here rather than looking like a log.

Two provenance notes, because this file travels between trees. It was captured from this ported
tree by the agent sandbox: section 1's ``Ran 278`` is this directory's own suite (the mirror in
``data-factory-v2/stage-4`` printed ``Ran 312`` for the same bytes -- the two suites differ by the
tests that cannot be ported, not by this patch), and section 3's cluster is a disposable
``pgserver`` holding 200 invented orders, so no duration in this file is a measurement of your
database. The measurement that closes checklist 5.3 is beside it, in
``frame-performance-student-run.txt``, and that one is yours.
