phase1-decision-counts.txt -- the D1/D2/D3 counts, measured on a database
=========================================================================

What this file is: the four counts ROADMAP phase 1 item 2 asks for (checklist 3.9),
taken from a PostgreSQL that holds the real Olist rows. Not from memory, not from a
notebook, not from a documentation figure. Every number below is a line of output from
the run described in section 1, and the SQL that produced it is printed with it.

Headline, so a reader does not have to dig:

    D1  orders with no order_approved_at        160 of 99,441   = 0.1609 %
    D2  orders with no review at all            768 of 99,441   = 0.7723 %
    D2  negative reviews (score <= 2)        14,575 rows over 14,533 orders
    D3  orders with more than one review        547  (543 with two, 4 with three)

The last row is not a rounding detail: 543 + 4 = 547, and 98,126 + 547 + 768 = 99,441.
The three counts add up to the table they came from, which is the only internal check
available without a second database.


1. HOW THE DATABASE CAME TO EXIST
---------------------------------
    cluster        pgserver (bundled PostgreSQL 16.2), data dir created for this run and
                   destroyed by it; unix socket only; nothing of the student's olist_db
    schema         stage-2/sql/001_create_olist_schema.sql, applied verbatim -- every
                   CHECK and every foreign key in that file was therefore enforced while
                   the rows went in (that is a finding, see section 2)
    load path      data_factory.database.load_csv, the function stage 1's load_olist is
                   built from: same typed conversion, same column reflection, same
                   product_name_lenght/product_description_lenght aliases
    tables loaded  customers, orders, order_reviews -- the three the counts need.
                   The other six were not loaded, and no number in this file depends
                   on them.
    interpreter    the sandbox python 3.11; sqlalchemy 2.1.8, psycopg2 as the driver

Load order matters and was respected: customers before orders (fk_orders_customer),
orders before order_reviews (fk_reviews_order).

The harness that drove all of this is not committed: the round asked for the counts, and
a script that executes its own evidence is what sql/README.md refuses to be. What is
committed is everything needed to re-measure by hand -- the SQL is printed in section 3
and the file names and sha256 values in section 2 pin the inputs.

                                    ec19ae3345ef9ecf   ->  orders is not in question

                                    Olist copy has lost the leading zero of
                                    customer_zip_code_prefix in 23,995 rows, so it
                                    violates ck_customers_zip ('^[0-9]{5,8}$') and the

Which review file the student's own database holds is answered without asking him:
section A.1 of docs/evidence/phase0-baseline.txt records order_reviews loaded=99,224 on
his PostgreSQL, and the same baseline records 99,441 orders, 112,650 order_items,
103,886 payments, 32,951 products, 3,095 sellers, 71 translations -- every one of which
matches the Olist mirror's file. One more corroboration, from this run and not from
memory: stage-2's DDL comment says review_id is not unique and 789 review ids are
reused; the query below, on this file, returns exactly 789 ids appearing more than once
(814 surplus rows). So the Olist copy is the file that produced both the DDL's note and
the student's row counts, and it is the one measured here.

Consequence, stated so nobody has to rediscover it: with this file D2 = 768 orders
without a review. With the other mirror's 100,000-row file every order has a review and
D2 would be 0. Before writing the no-review policy, run the one query in section 4
against olist_db; the decision is not the same in the two worlds.

=== D1 orders with no order_approved_at ===
  SELECT COUNT(*) AS orders_total,
  COUNT(*) FILTER (WHERE order_approved_at IS NULL) AS missing_approved_at,
  ROUND(100.0 * COUNT(*) FILTER (WHERE order_approved_at IS NULL) / COUNT(*), 4)
  AS missing_pct
  FROM olist.orders
  orders_total | missing_approved_at | missing_pct
  99441 | 160 | 0.1609

=== D1 which statuses carry the missing approval ===
  SELECT order_status, COUNT(*) AS rows_total,
  COUNT(*) FILTER (WHERE order_approved_at IS NULL) AS missing_approved_at,
  ROUND(100.0 * COUNT(*) FILTER (WHERE order_approved_at IS NULL) / COUNT(*), 2)
  AS missing_pct
  FROM olist.orders
  GROUP BY order_status
  HAVING COUNT(*) FILTER (WHERE order_approved_at IS NULL) > 0
  ORDER BY missing_approved_at DESC

  canceled | 625 | 141 | 22.56
  delivered | 96478 | 14 | 0.01

=== D2 orders with no review at all ===

3b. THE MIRROR QUESTION, CLOSED BY A RUN ON THE STUDENT'S DATABASE

The query in section 4 was run by the student against `olist_phase0_test` after this log
was written, and it returned **768** -- the same figure measured here. So the file his
database holds is the 99,224-row revision, D2 = 768 stands on both databases, and the

Provenance of this paragraph, stated as precisely as the rest: it is a number the student

4. WHAT THIS DOES NOT SAY, AND THE ONE COMMAND THAT WOULD
----------------------------------------------------------
It does not say what olist_db contains. It says what the public Olist files that agree
with the phase-0 baseline contain, in a database built from the versioned DDL. Those are
the same rows only if his raw dir holds the same revision -- which the row counts
suggest and the reused-id figure (789) nearly proves, but which he should confirm in
ten seconds:

    SELECT COUNT(*) FILTER (WHERE order_approved_at IS NULL)      AS d1_missing_approval,
           (SELECT COUNT(*) FROM olist.orders)                    AS orders_total,
           (SELECT COUNT(*) FROM olist.orders o
              LEFT JOIN (SELECT DISTINCT order_id FROM olist.order_reviews) r
              USING (order_id)
             WHERE r.order_id IS NULL)                            AS d2_orders_without_review,
           (SELECT COUNT(*) FROM (SELECT order_id FROM olist.order_reviews
                                  GROUP BY order_id HAVING COUNT(*) > 1) m)
                                                                  AS d3_multi_review_orders
    FROM olist.orders;

Three more limits, so the numbers are not over-read:

* order_reviews.review_creation_date is later than order_approved_at in 99,191 of the
  99,224 rows (only 33 are at or before it). The label therefore exists strictly after
  the decision moment, always -- which is why the whole challenge is about what the
  features may look at, and why the leakage audit is worth 25 % of the grade.
* 156 reviews belong to the 160 orders that have no approval timestamp, so D1 and D2
  overlap; a policy for one is a policy for part of the other.
* the window is truncated at the end: 2018-09 has 16 orders and 2018-10 has 4, and the
  missing-approval rate in those months is 93.75 % and 100 %. A boundary placed on
  "the last month of the file" evaluates on 16 rows. This is measured, not argued, and
  it belongs to checklist 3.6.
