``--rev`` is left at its default here, and that is the point of running it on this side: ``HEAD~1``

which is exactly the code that refused the endpoint. On the tree the patches were authored in, the
same section names the commit instead (``--rev 3236580``); the two logs are otherwise the same run.

read it as:

* section 1 is this repository's own offline suite on the plain interpreter -- ``Ran 292 tests …
  OK (skipped=15)``, fourteen cases more than the same tree measured before this patch, no
  ``psycopg``, no server, no network;
* section 2 is the red/green half, and the red half is the previous commit's ``src/``, extracted
  with ``git archive`` rather than edited out of the fixed tree. Same probe, same response file, so
  the two blocks differ only by the patch. The refusal printed there is the sentence a live
  ``--fetch`` answered with -- ``returned no 'result' key (top level: list)`` -- and on this side of
  the patch the same body is three rows, with ``3.04`` where a pt-BR-tinged reader would have put
  ``304``;
* section 3 is the shipped ``capstone external`` command pointed at a server on 127.0.0.1 that
  answers with the recorded body. It counts the requests, because "one request per run" is a policy
  the module states and had never measured: one for ``--fetch``, zero for the status block. The two
  derived bodies -- ``uf`` removed, and level changed to ``N7`` -- are refused with exit 69 and a
  sentence, and no traceback;
* section 4 is the only section that needs the dev extra: a disposable cluster, stage-2's DDL found
  beside this stage, the five migrations applied, then ``external --load`` for real. Read back from
  the table: three rows, two non-null values, the missing municipality still ``NULL``, and ``3.04``
  as a numeric. The match rate says ``no customer keys at all`` because this cluster has an empty
  ``olist`` -- it is a plumbing check, not the project's number;
* the log is flattened where flattening is honest: unittest's elapsed clause, the scratch directory
  ``git archive`` unpacked into, and the ephemeral port of the local server are all replaced by a
  placeholder, so a second run of the harness can be compared to this one line for line.

what this file does **not** establish:

* it is not a call to ``servicodados.ibge.gov.br``. That host answers from the student's machine and
  not from the sandbox this was run in, so the live verdict of checklist 12.5 is still to be
  produced by ``capstone external --fetch`` / ``--load`` / ``--report`` and written into
  ``report.md`` either way;
* the response file is a transcription of the student's measurement, not their raw body: the codes,
  the year, the variable name, the unit and the number ``3.04`` are what they read off the endpoint,
  while the locality names are placeholders and the ``uf`` objects are the fields their
  transcription did not carry (``docs/evidence/ibge-4714-614-sample.json``, and item 8 of
  ``decisions.md``).
* nothing in it is a claim about the frame's ``feature_query_ms`` ceiling -- that verdict lives in
  ``frame-performance-student-run.txt``.
